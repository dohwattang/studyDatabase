📌 이 시간의 목표

본격적인 SQL 실습에 앞서, 데이터를 어떻게 설계하는가를 먼저 이해한다. SQL은 '잘 설계된 데이터'에 질문하는 언어다. 설계를 모르면 쿼리도 겉돈다. 이 내용은 SQLD 자격증 1과목(데이터 모델링의 이해)의 기초이기도 하다. 어려운 정규화 이론은 개념만 짚고, 실무·시험에 꼭 필요한 기본기에 집중한다.

데이터베이스와 DBMS

데이터베이스(DB)는 여러 사람이 공유하기 위해 체계적으로 모아둔 데이터의 집합이다. 이를 관리하는 소프트웨어가 DBMS(DataBase Management System)다.

특징의미
통합된 데이터중복을 최소화하여 모음
저장된 데이터컴퓨터가 접근 가능한 매체에 저장
공유 데이터여러 사용자·프로그램이 함께 사용
운영 데이터조직 운영에 꼭 필요한 데이터

관계형 데이터베이스 (RDB)

데이터를 표(table) 형태로 저장하고, 표들 사이의 관계로 연결하는 방식이다. 오늘날 가장 널리 쓰이며, MySQL·Oracle·SQL Server가 모두 여기에 속한다.

용어설명게임 DB 예
테이블(Table)데이터를 담는 2차원 표user, payment
행(Row/Tuple)한 건의 데이터(레코드)유저 1명
열(Column/Attribute)데이터의 속성(필드)nickname, level

SQL의 3가지 분류

SQL 명령은 역할에 따라 세 갈래로 나뉜다. SQLD 시험과 실무에서 자주 등장하는 분류다.

분류풀이대표 명령이 수업에서
DDL데이터 정의어CREATE, ALTER, DROP1·2주차
DML데이터 조작어SELECT, INSERT, UPDATE, DELETE3주~13주
TCL트랜잭션 제어어COMMIT, ROLLBACK13주차
💡 DCL도 있다

권한을 다루는 GRANT·REVOKE를 DCL(데이터 제어어)이라 한다. 이 수업 범위는 아니지만, SQLD에서 'SELECT는 무슨 어(語)인가?' 같은 분류 문제가 자주 나오니 표를 기억해두자. (정답: DML)

엔티티 · 속성 · 관계 · 키

1.DB·모델링 개념
2.엔티티·속성·관계·키

데이터 모델링의 핵심 4인방 — 엔티티 · 속성 · 관계 · 식별자를 익힌다. SQLD 1과목에서 가장 많이 나오는 개념이자, 모든 DB 설계의 출발점이다.

데이터 모델링이란

현실 세계의 데이터를 테이블 구조로 옮기기 위한 설계 작업이다. 집을 짓기 전 설계도를 그리듯, DB를 만들기 전에 "어떤 데이터를 어떤 표에 담을지" 정한다. 보통 개념적 → 논리적 → 물리적 3단계로 구체화한다.

① 엔티티 (Entity)

데이터로 관리할 대상이다. 보통 테이블 하나가 된다. "유저", "캐릭터", "아이템"처럼 명사로 표현된다.

💡 엔티티의 조건

좋은 엔티티는 ▲업무에 꼭 필요하고 ▲유일하게 식별 가능하며 ▲두 개 이상의 인스턴스(행)를 가지고 ▲속성을 포함한다. 게임 DB의 user는 8명(인스턴스)을 담고, 각자 닉네임·레벨(속성)을 가지므로 좋은 엔티티다.

② 속성 (Attribute)

엔티티가 가지는 세부 정보 항목이다. 테이블의 컬럼에 해당한다. user 엔티티의 속성: user_id, nickname, level, age …

③ 관계 (Relationship)

엔티티들이 서로 어떻게 연결되는가이다. 관계의 수(카디널리티)가 핵심이다.

관계의미게임 DB 예
1:1한 쪽에 한 쪽유저 1명 — 프로필 1개
1:N한 쪽에 여럿유저 1명 — 캐릭터 여러 개
N:M여럿에 여럿유저 여럿 — 아이템 여럿(결제로 연결)
📌 N:M은 중간 테이블로

유저와 아이템은 여러 명이 여러 아이템을 산다(N:M). 이걸 직접 잇지 않고 payment(결제) 테이블을 중간에 둬서 1:N + 1:N으로 푼다. 이 '중간 테이블'이 실무 설계의 단골 패턴이다.

④ 식별자와 키 (Key)

각 행을 구별하는 열쇠다. SQLD·실무 모두에서 매우 중요하다.

키설명
기본키 (Primary Key)행을 유일하게 식별. 중복·NULL 불가. 테이블당 1개
후보키 (Candidate Key)기본키가 될 수 있는 자격을 가진 키
외래키 (Foreign Key)다른 테이블의 기본키를 참조. 테이블 간 연결고리
키 관계 개념
-- user의 기본키 user_id를, payment가 외래키로 참조
user     : user_id(PK), nickname, level ...
payment  : payment_id(PK), user_id(FK→user), amount ...

-- 이 FK 덕분에 '없는 유저의 결제' 같은 잘못된 데이터가 막힌다

ERD — 설계도 읽기

ERD(Entity Relationship Diagram)는 엔티티와 관계를 그림으로 나타낸 설계도다. SQLD 시험에 ERD 해석 문제가 나오고, 11주차 조인에서 다시 만난다.

게임 DB · ERD
game_server (1) ──< user (1) ──< character_tb >── (1) job
                            │
                            └──< payment >── (1) item

  ──<  : 1:N 관계 (한 서버에 여러 유저)
  >──  : N:1 관계 (여러 캐릭터가 한 직업)

정규화 — 개념만 알아두기

정규화는 중복을 줄이고 데이터를 깔끔하게 나누는 설계 원칙이다. 예를 들어 결제마다 유저 닉네임을 반복 저장하면 낭비이고 수정도 번거롭다. 그래서 유저는 user 테이블에, 결제는 payment 테이블에 나눠 저장하는 것 — 이게 정규화의 기본 아이디어다.

⚠️ 정규화는 깊이 안 들어간다

1정규형·2정규형·3정규형 같은 단계 이론은 이 수업 범위를 넘어선다. 지금은 "중복을 줄이려고 테이블을 적절히 나눈다"는 개념만 잡으면 충분하다. 왜 테이블이 6개로 나뉘어 있는지 이해하는 것, 그것이 정규화를 체감하는 첫걸음이다. SQLD를 본격 준비할 때 별도로 학습하면 된다.
